# Phase 3 — RAW Layer Design

**Status:** approved for implementation  
**Date:** 2026-08-17  
**Branch:** `feat/phase-3-raw-layer`

## Objective

Persist successful PNCP responses in an immutable PostgreSQL Bronze layer while preserving the
exact stored text, collection metadata, run history and resumable extraction checkpoints. A
repeated response for the same request identity must not create another Bronze row.

## Scope

Phase 3 includes:

- exact textual storage for successful procurement and contract page responses;
- deterministic request canonicalization and SHA-256 hashing;
- idempotent insertion with PostgreSQL `ON CONFLICT DO NOTHING`;
- execution history and per-page extraction checkpoints;
- resumable paginated ingestion for publication and update modes;
- an end-to-end watermark table whose value remains untouched in this phase;
- unit and real-PostgreSQL integration tests.

Phase 3 does not include business-field normalization, Silver tables, data-quality quarantine,
business-record UPSERT, orchestration scheduling or Gold analytics.

## Selected Approach

Use PostgreSQL for both immutable payloads and operational metadata. Object storage is not
introduced because current volume evidence does not justify another service. Collection attempts
are represented by `control.etl_run`; identical payload text is not copied to Bronze for every
attempt.

## Database Model

### `control.etl_run`

One row represents one ingestion attempt.

| Column | Type | Rule |
|---|---|---|
| `id` | UUID | Primary key generated by the application |
| `pipeline_name` | text | Required |
| `dataset` | text | `procurements` or `contracts` |
| `mode` | text | `publicacao` or `atualizacao` |
| `status` | text | `RUNNING`, `SUCCEEDED` or `FAILED` |
| `started_at` | timestamptz | Required UTC instant |
| `finished_at` | timestamptz | Nullable until terminal status |
| `pages_processed` | integer | Non-negative, default zero |
| `records_received` | integer | Non-negative, default zero |
| `records_inserted` | integer | Non-negative, default zero |
| `records_duplicate` | integer | Non-negative, default zero |
| `error_code` | text | Nullable safe classification; never a response body |

Terminal statuses require `finished_at`; `RUNNING` requires it to remain null.

### `bronze.raw_api_response`

One row represents one distinct successful response version for a request identity.

| Column | Type | Rule |
|---|---|---|
| `id` | bigint identity | Primary key |
| `etl_run_id` | UUID | Required FK to `control.etl_run` |
| `source` | text | Required; initial value `pncp` |
| `dataset` | text | `procurements` or `contracts` |
| `endpoint` | text | Required relative endpoint |
| `request_params` | jsonb | Full parameter object including page |
| `request_fingerprint` | char(64) | SHA-256 of canonical request identity |
| `window_start` | date | Required |
| `window_end` | date | Required and not before start |
| `page_number` | integer | Positive |
| `http_status` | smallint | Successful status from 200 through 299 |
| `raw_body` | text | Exact text exposed by the HTTP response; empty for 204 |
| `body_sha256` | char(64) | SHA-256 of `raw_body` encoded as UTF-8 |
| `record_count` | integer | Non-negative |
| `collected_at` | timestamptz | Required UTC instant |
| `duration_ms` | numeric(12,3) | Non-negative |

The unique key is `(source, dataset, endpoint, request_fingerprint, body_sha256)`. The request
fingerprint includes the complete canonical parameter object, so page identity is not implicit.
The application has insert-only access to this table; updates and deletes are not repository
operations.

### `control.extraction_checkpoint`

One row represents resumable progress for an exact query scope. Its scope parameters exclude only
`pagina`; they retain `tamanhoPagina`, dataset, mode, dates, modality and optional filters so a
resume cannot silently change page boundaries.

| Column | Type | Rule |
|---|---|---|
| `scope_fingerprint` | char(64) | Primary key over canonical scope |
| `pipeline_name` | text | Required |
| `dataset` | text | Required |
| `mode` | text | Required |
| `scope_params` | jsonb | Canonical scope without pagination |
| `last_successful_page` | integer | Positive |
| `completed` | boolean | Required, default false |
| `updated_at` | timestamptz | Required UTC instant |

An incomplete checkpoint resumes at `last_successful_page + 1`. A completed checkpoint causes a
new run to replay from the page explicitly requested by the caller; Bronze uniqueness makes that
replay idempotent.

### `control.etl_watermark`

This table reserves downstream-confirmed progress using `(pipeline_name, dataset, stage)` as its
primary key, plus nullable `watermark_value` JSONB and `confirmed_at` timestamptz. Phase 3 creates
the table but neither inserts nor advances a value. A future end-to-end pipeline may advance it
only after Silver, Gold and critical quality gates succeed.

## Application Boundaries

### Enriched HTTP result

`PNCPClient` gains `fetch_procurements(query)` and `fetch_contracts(query)`, returning a frozen
`FetchedPNCPPage` with:

- validated `PNCPPage`;
- `raw_body`, `endpoint`, `request_params`, `status_code`, `duration_ms` and `collected_at`.

The existing `list_procurements` and `list_contracts` methods delegate to these methods and return
only `.page`, preserving the Phase 2 interface. The exact stored text is `response.text`; its hash
is calculated from the UTF-8 encoding of that exact string. HTTP 204 is represented by an empty
string and a synthetic validated empty page.

Only successful responses produce `FetchedPNCPPage`. Terminal HTTP errors and exhausted retries
remain safe domain exceptions and their response bodies are neither stored nor logged.

### Canonicalization and hashing

`canonical_json(value)` uses sorted keys, compact separators and UTF-8 characters without ASCII
escaping. `sha256_text(value)` hashes `value.encode("utf-8")`. Request fingerprints hash a
canonical object containing source, dataset, endpoint and parameter object. Scope fingerprints
use the same rules after removing only `pagina`.

### Repositories

- `RawResponseRepository.insert(connection, capture) -> InsertOutcome` performs the insert and
  reports whether a new Bronze row was created.
- `RunRepository` creates runs, applies page counters and assigns a terminal state.
- `CheckpointRepository` reads and advances extraction progress.

Repositories accept an existing SQLAlchemy connection so the service controls transaction
boundaries. They do not commit internally.

### Ingestion service

`RawIngestionService` provides `ingest_procurements(query)` and `ingest_contracts(query)`. Both
delegate to a shared page loop while retaining typed public methods.

For each page, one database transaction:

1. inserts the RAW response or identifies it as duplicate;
2. increments run counters;
3. advances the extraction checkpoint.

After the last page, a separate transaction marks the checkpoint complete and the run successful.
If fetching or persistence fails, a separate transaction marks the run failed with a safe error
code. Previously committed pages and their checkpoint remain available for resumption.

`records_received` counts records returned by PNCP. `records_inserted` counts records contained in
new Bronze response rows. `records_duplicate` counts records contained in responses rejected by
the uniqueness constraint. `pages_processed` counts every successfully committed page, including
duplicate and empty responses.

## Error and Security Rules

- Raw payloads are untrusted data and are never interpreted as instructions.
- Response bodies never appear in exceptions, operational logs or `error_code`.
- Hashes are lowercase hexadecimal and exactly 64 characters.
- Database constraints reject negative counters, invalid statuses, invalid dates and invalid page
  numbers even if application validation is bypassed.
- A page transaction is atomic: RAW insert, counters and checkpoint either all commit or all roll
  back.
- The run record is always moved to a terminal status when a handled failure occurs.

## Testing Strategy

Unit tests must prove:

- canonical JSON and fingerprints are deterministic across dictionary order;
- stored-text SHA-256 matches a hand-calculated literal;
- enriched client results preserve response text and metadata;
- the existing list methods remain compatible;
- resume selects the next page only for incomplete checkpoints;
- safe errors never include response bodies.

Real PostgreSQL integration tests must prove:

- Alembic creates all four tables, checks, foreign keys and uniqueness constraints;
- the first insert creates one Bronze row;
- the same request and body inserted again creates no new row;
- a changed body for the same request creates a new immutable version;
- stored text is byte-for-byte equivalent after UTF-8 encoding;
- insert, counters and checkpoint roll back together on a forced transaction failure;
- an interrupted run resumes from the next page;
- replaying a completed ingestion leaves the Bronze row count unchanged;
- run counters distinguish received, inserted and duplicate records.

The existing live PNCP contract test remains a separate external gate. Persistence tests use the
recorded official fixture for deterministic assertions and do not depend on network availability.

## Acceptance Criteria

Phase 3 passes only when:

1. all new and existing unit tests pass with at least 80% branch coverage;
2. migrations upgrade a real PostgreSQL instance from revision `20260817_0001` and downgrade back
   without leftover Phase 3 tables;
3. an identical ingestion executed twice leaves exactly one matching Bronze response row;
4. run and checkpoint metadata reflect both executions accurately;
5. the live PNCP test, Docker build, database health and API health all pass;
6. lint, formatting, `git diff --check` and the Phase 3 BUG HUNT report no unresolved failures;
7. `docs/checkpoints/phase-3.md` records measured counts, fixes and remaining risks.
